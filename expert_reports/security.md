# EatOS security and privacy review

Scope: SECURITY.md, core (vault, validate, sync, photo, llm-ask, rules, aspire, quickadd, ask, memory, drivers), apps/api, app (llm, photo, secure, kernel, sync, files, Unlock, ProtectionSettings, FoodProfile, LlmSettings, QuickAdd, integrations, wishes, taste), workflows, Dockerfile/compose.
Method: read-only plus throwaway scripts (in the scratchpad; no repo files touched). Items marked **[repro]** were reproduced.

Good news first: the vault is sound (scrypt, XChaCha20-Poly1305, random 24-byte nonce, params+salt bound as AAD); event validation is allow-list based and runs on load/merge/sync/backup; the LLM output is schema-checked and never touches hard safety rules; no HTML rendering (React Native text only, no `dangerouslySetInnerHTML`/WebView found); the container runs as non-root; lockfile is frozen in CI.

## Details, exploit and fix

**1. API has no auth and `CORS: *`.** `x-user-id` is both identity and (as the sync code) the only secret; default is the shared user `me`. `GET /v1/export` with no custom header is a CORS "simple" request, and the response sends `ACAO: *`, so any web page the owner opens can `fetch('http://127.0.0.1:8787/v1/export')` (or DNS-rebind, since `Host` is not checked) and read the household's health and diet data; `DELETE /v1/data` is allowed by the preflight and erases it. Repro: unauthenticated `/v1/export` returned 200 with `ACAO=*`, and `DELETE` of another id returned 200. Compose publishes the port on all interfaces and defaults `EATOS_CORS_ORIGIN` to `*`; SECURITY.md only mentions this as a "known limit". Codes are 4 to 64 chars with no rate limit, so short codes are enumerable.
Fix: require `Authorization: Bearer <random 128-bit token>` (server-generated, hashed at rest) instead of using the code as identity; remove the default `me`; default CORS to no origin (fail closed, refuse `*` when a data key is set); reject unexpected `Host`; add per-IP and per-token rate limits and a 429; require min 16-char generated codes in the app. Test idea: request without a token returns 401; `OPTIONS` from a foreign `Origin` has no `ACAO`; 20 bad tokens from one IP return 429.

**2. ReDoS in `ask.ts:48`** `/(\d+)\s*(?:min|mins|minutes|m\b)/` is quadratic on a long digit run with no unit. Measured: 10k digits 96 ms, 20k 414 ms, 40k 1.9 s, 200k 47 s; via the API, 30k digits 0.86 s and 100k digits 9.2 s, and 1 MB (body cap) is about 20 minutes of a blocked event loop for every user. In the app the same input arrives via `?q=` (finding 15). Also `parseAsk` is called on the full text after the LLM path slices to 500.
Fix: cap input (`text.slice(0, 500)`) at the top of `parseAsk`/`Kernel.ask`/`/v1/ask`, and use `(\d{1,4})` (bounded). Test: `parseAsk('1'.repeat(200000)+'x')` finishes under 100 ms; API returns 400 for text over 500 chars.

**3. ICS infinite loop.** `RRULE:FREQ=WEEKLY;BYDAY=XX` leaves `days=[]` after the filter; the outer `for (w...)` never breaks, so the JS thread hangs (killed my test at 10 s). Import of any shared .ics or a pasted calendar freezes the app permanently (the UI thread on web). Fix: `if (!days.length) return [e.start]`, plus an iteration cap (`w < 5200`) and `Number.isFinite(interval)`. Test: parseIcs with `BYDAY=XX` returns within 1 s; `INTERVAL=abc` does too.

**4. Prototype pollution.** `preferences()` does `out[e.foodId] ??= {...}` on `{}`. A `feedback` event with `foodId:"__proto__"` passes `str()`, is accepted by `readBackup`, sync and the API, and after `recommend()` `({}).score` is `NaN` on every object in the process; `foodId:"constructor"` sets `Object.score`. On the server this poisons all users until restart. Fix: use `Map` or `Object.create(null)` in `memory.ts` (and `lastNever/lastLiked`), and make validate `str()` for id-like fields reject `__proto__`, `constructor`, `prototype`. Also state.ts `pantry.used` with `itemId:"__proto__"` reads `Object.prototype` as an item. Test: after reading a backup with `foodId:'__proto__'` and running `recommend`, `({} as any).score === undefined`.

**5. `in` operator on a plain object.** `'toString' in DIET_RANK` is true, so `member.diet:'toString'` validates (backup, sync, API) and `parseMenu` accepts `diet:"constructor"`. `DIET_RANK[x] > fn` is `false`, so `menuBlocker` returned `undefined` for a vegan with a dish whose diet is `toString` (repro), and `hardProblem` compares the same way. A crafted menu JSON or event therefore defeats the diet check, the safety property the product promises. Fix: `Object.hasOwn(DIET_RANK, d)` in both places, and typed allow-list arrays like the others. Test: `isValidEvent` rejects `diet:'toString'`; `parseMenu` reports an unknown diet.

**6. Integrity of safety data.** Valid-shaped events are fully trusted: a sync server, a MITM on `http://`, anyone who learns or guesses the code, or an untrusted plain backup can submit a later `profile.set` that drops allergens, rules or `minor`, and the UI reports "Restored N records" with no diff. Fix: sign events end to end (per-household key derived on device, HMAC or AEAD the sync payload, so the server cannot forge or read); show a confirm screen that names changes to allergies/rules/conditions on restore and on first sync; require `https://` except for localhost/RFC1918; keep a "profile history" so an unwanted change can be undone. Test: merging a `profile.set` that removes an allergen via `restore` returns a flagged "safety change" list.

**7. Per-user cost.** With `EATOS_DATA_KEY` set, the first request for any new `x-user-id` (even `GET /v1/state`) runs `Vault.create` (scrypt about 200 ms, 32 MB) and caches the entry forever: 5 ids cost 1.0 s and about 140 MB RSS. Anyone reachable can exhaust CPU/RAM; `/v1/sync` or `/v1/events` also creates files with no per-user size cap (the 1 MB body cap is per request). Fix: auth first (finding 1), lazy-create the entry only on write, LRU-evict idle entries, per-user quota (events and bytes), disk-free check. Test: 100 GETs for random ids stay under 50 MB and under 2 s.

**8. KDF DoS.** `unlock` accepts N up to 2^20, r up to 16, p up to 4 from the file. Measured: N=2^18 took 18.6 s (Node) before failing authentication; 2^20 with r=16 asks for 2 GB (Node refused at maxmem; JS in a phone/browser would stall or crash). Fix: accept only N<=2^17, r<=8, p=1 for imports (or exactly the app's own params), and run the KDF only after the envelope size is sane. Test: `readBackup` of an envelope with N=2^20 rejects as "Unsupported key settings" in under 50 ms.

**9. Secrets at rest.** The Anthropic key and sync code live in AsyncStorage (localStorage on web, `dangerouslyAllowBrowser: true`) in plaintext unless device protection is on, which is optional and off by default. Fix: use `expo-secure-store` (Keychain/Keystore) on native, and on web strongly steer to the protection toggle before saving a key; show masked key and a "revoke" link. Also never include `e.message` of SDK errors in UI without scrubbing (`photo.ts:157` shows it); scrub `sk-ant-` patterns. Test: `redact()` strips `sk-ant-...` from any displayed error.

**10. Privacy copy honesty.** (a) `LlmSettings.tsx:28` says "Only the sentence you type is sent" but the same toggle and key also enable Photo add, which sends the whole photo (receipts show names/addresses/card tails; shelves show faces and rooms); SECURITY.md also omits photos. (b) `integrations.tsx:183` "it all stays on your device" is false once sync, Claude or photo is on. (c) The typed sentence is free text and can contain a condition ("I'm diabetic, pregnant..."), so "health data is never sent" (`FoodProfile.tsx:129`, LlmSettings) should say "your saved profile is never sent; whatever you type is". (d) `app.json` permissions say photos are "not stored", but temp files remain (11). (e) "Rules ... are never broken" (`FoodProfile.tsx:88`) over-promises: matching is by ingredient word and defaults differ by household. Fix: separate consent toggles per feature (Ask text, Photo), each with one plain sentence on what leaves, to whom, and a "withdraw" control; align SECURITY.md. Test: a copy snapshot test that fails if "stays on your device" appears next to a Claude toggle.

**11. Photo privacy.** `ImageManipulator` re-encodes to JPEG, which should drop EXIF/GPS (add a test on a fixture, I did not run a device); camera and picker output, the resized copy, and `DocumentPicker` copies (`copyToCacheDirectory: true`, health exports and ICS) are never deleted. Fix: `FileSystem.deleteAsync(uri,{idempotent:true})` in `finally` for every temp URI; show a preview with a Send/Cancel step and a "receipts may contain personal details" note; for web, release the object URL (already done). Test: after `preparePhoto` the temp file no longer exists.

**12. Erasure.** `wipe()` deletes the server copy first, but if it fails it still clears `syncConfig` (`setSyncConfig(defaultConfig)`), so the code is lost and server data persists with no retry. The server also keeps `<id>.json.tmp` only during a write. Fix: keep a "pending server deletion" record (url, code) until confirmed, retry on next launch, and show it plainly. Test: with a failing server, `wipe()` returns `serverDeleted:false` and `pendingDeletion` remains.

**13. CI/supply chain.** `ci.yml`, `eas-build.yml` have no `permissions:` block (token scope then follows repo default), `release.yml` has `contents: write` for the whole job while `pnpm install` and Playwright run, and `actions/checkout` keeps the token in `.git/config`; `pages.yml` gives `id-token: write` to the build job; actions pinned to tags not SHAs; `expo-github-action` uses `eas-version: latest`; CI also triggers on `claude/**` pushes. pnpm 10 skips dependency install scripts by default, but there is no explicit `onlyBuiltDependencies`. Fix: top-level `permissions: contents: read`; set `persist-credentials: false`; split release into build (read) and publish (write) jobs; pin actions by SHA (dependabot); pin `eas-version`; add `pnpm audit --prod` and a lockfile-diff review. No secret is echoed in logs (EXPO_TOKEN only on manual runs).

**14. Wish cost.** `findWishFood` builds a `RegExp` per (word, catalog food) in `hasWord`; the API caps wishes at 200 chars but `Kernel.wish`, the app `TextInput` and wish events (500) do not. 100 KB measured 90 ms (fine) but a 1 MB paste of distinct words scales with words x catalog. Fix: cap at 200 in `alternatives`, add `maxLength={200}` in `wishes.tsx`, escape once and precompute word sets. Test: `kernel.wish('a'.repeat(1e6))` returns quickly and unchanged for 200-char input.

**15. Deep link.** `eatos://ask?q=...` or `/ask?q=` is parsed immediately; with Claude on it sends up to 500 chars to Anthropic using the user's key and spends their quota, and it feeds finding 2. Fix: prefill the field only, require a tap, clamp length. Test: opening `/ask?q=x` makes no completer call.

**16. Silent drop on save.** `load()` filters invalid events, then every later `save()` writes the filtered log back, permanently deleting records if the validator is ever tightened (or a bug rejects good ones). Fix: keep a `quarantine` list and write it back, or back up the file before rewriting. Test: a log with one unknown event type still contains it in the file after a new event is added.

**17. Shared origin.** Project pages share `https://<user>.github.io`; localStorage is per origin, not per path, so a sibling repo's page (or any XSS there) can read `eatos.events.v1`, `eatos.llm.config`, `eatos.sync.config`. Fix: custom domain or subdomain for the app, and encourage device protection on web; document in SECURITY.md.

**19/20. Time and size bounds.** Reject `at` more than a day in the future and before 2000; clamp `nutrients` and `ml`; cap total events per user (for example 500k) and bytes. Test: `isValidEvent({type:'water.logged',at:8e15,ml:200})` is false.

## DPDP Act 2023 (India) in short

Applicability: duties fall on a Data Fiduciary (whoever decides purpose and means). For the purely on-device build, the developer receives no personal data, so the developer is plausibly not processing; and an individual using it for personal or domestic purposes is outside the Act (s.3(c)(i)). Self-hosted sync for one household is the same domestic case. This changes if the project (or a publisher in India) runs a hosted sync server, collects crash logs or analytics, ships a shared Claude key, or runs a managed service for other people: then it is a fiduciary and the points below bind it. The DPDP Rules were notified in late 2025 with phased commencement (verify current dates with counsel). Health and religion are not a special category under the Act, but the security safeguard duty and penalties (up to INR 250 crore) apply to all personal data.
- Consent and notice (s.5-6): consent must be free, specific, informed, for a stated purpose, with an itemised notice and withdrawal as easy as giving. Today there is no notice screen; sync, Claude Ask and Photo have no per-purpose consent record. Add a one-screen notice at onboarding, per-feature toggles (finding 10) and a "withdraw" that also deletes the key and server data.
- Children (s.9): under 18 needs verifiable parental consent, and no tracking, behavioural monitoring or targeted ads. The app has a `minor` condition (`FoodProfile.tsx:53`) but no age gate or guardian flow. Minimum: when `minor` is set, disable sync, Claude and photo unless an adult confirms in the app; no analytics ever; state it in the notice. For fully local use this is a design guardrail rather than a legal duty.
- Erasure and correction (s.12): in-app "Delete all data" exists; fix finding 12 and add a correct-my-data path (events are append-only, so provide "edit profile" plus compaction).
- Security safeguards and breach (s.8(5)-(6)): encryption at rest is optional; fix 1, 6, 7, 9. If a hosted server exists, write a breach runbook: notify the Board and each affected person without delay; keep logs. SECURITY.md lacks an incident process and a contact other than a GitHub advisory.
- Cross-border (s.16) and processors: sending text or photos to Anthropic is a transfer by the user with the user's own key; disclose it, and name Anthropic's retention terms in the notice.
- Grievance officer (s.13) and notice in English plus Eighth Schedule languages apply only if a fiduciary.
